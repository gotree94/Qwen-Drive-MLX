## 0. 개요 — 이걸 왜 하느냐

| 항목 | torch (원래) | MLX (이식 후) | 비고 |
|---|---|---|---|
| 탑뷰(TopView) 생성 | 3.4초 | **0.64초** (카메라 1대) / 1.20초 (3대) | 약 5.3배 |
| 경로 계획(Path Planning) | 4.5초 | **1.4초** | 약 3.2배 |
| 품질 | — | 8비트에서 **품질 손실 없음** | |
| Alpamayo 2 Super 34B (맥) | 72GB — 올리지 못함 | **13.6~14.2초**, 메모리 34GB | VLM만 MLX + KV 캐시 브리지 |

핵심 결론: **속도 향상의 주역은 양자화가 아니라 프레임워크(MLX)다.** 8비트로 줄여도 품질은 유지되지만, 실제로 체감되는 차이는 MLX가 Apple Silicon의 통합 메모리·GPU 파이프라인을 직접 다루기 때문입니다.

## 1. 모델 구조 이해 — 부품 셋 (필수 선행 지식)

Qwen-Drive 4B는 세 파트로 구성됩니다.

```
① 언어 모델 (VLM)  ──►  ② 플래너  ──►  ③ 인식 헤드
     (기저 특징)         (경로 계획)      (탑뷰·감지)
```

- **② 플래너와 ③ 인식 헤드는 ①의 특징(feature)으로 학습**되었습니다.
- 따라서 **①을 다른 모델로 통째로 바꾸면 ②·③이 기대하는 특징 분포가 깨져 탑뷰가 사라집니다.**
- 실습 시 주의: ①을 교체하고 싶다면 ②·③까지 재학습(또는 증류)해야 합니다. 단순 교체는 불가능합니다.

> 이 구조적 제약이 곧 "증류로 옮겨지지 않는 것" 이야기와 이어집니다. (§7 참고)

## 4. 기본 실행 — 탑뷰 & 경로 계획

### 4-1. 탑뷰(TopView) 추론

```python
# 예시 구조 (저장소의 추론 스크립트에 맞춰 조정)
from mlx_lm import load, generate

model, tokenizer = load("./qwen-drive-mlx-8bit")

# 카메라 1장 입력 → 탑뷰
result = generate(model, tokenizer, prompt=탑뷰_프롬프트, max_tokens=...)
```

기대 성능:

| 구성 | 1회 추론 시간 |
|---|---|
| 카메라 1대 | **0.64초** |
| 카메라 3대 | **1.20초** |

### 4-2. 경로 계획(Path Planning)

- 기대 시간: **1.4초** (torch 기준 4.5초)
- 같은 입력(카메라 프레임)에 대해 플래너 헤드를 호출합니다.

### 4-3. 실측 검증 — 실차 주행 로그

- 실차 주행 **3회, 총 113분** 기록이 있습니다.
- **카메라 1대·3대 구성 모두**에서 주행 검증되었습니다.
- 로그/비주얼이 저장소 또는 영상에 포함되어 있으므로, 재현 시 결과 비교 기준으로 삼으세요.

## 5. (심화) Alpamayo 2 Super 34B를 맥에서 돌리기

### 5-1. 왜 직접 torch로는 안 되는가

- 34B 모델을 torch로 올리면 **72GB** — Apple Silicon 어디에도 안 들어갑니다.
- 그래서 **VLM(언어 모델)만 MLX로 갈아 끼우고, 전문가 헤드(플래너·인식)는 별도**로 두는 구조를 만듭니다.
- **KV 캐시를 전문가 쪽으로 넘기는 "브리지"** 를 구성한 핵심 포인트입니다.

```
[카메라 입력] ─► VLM (MLX, Apple GPU) ──KV 캐시──► 전문가 헤드 (별도 연산)
                  34GB 상주                     플래너/인식
```

### 5-2. 실행 결과

| 항목 | 수치 |
|---|---|
| Alpamayo 2 Super 34B (맥) | **13.6 ~ 14.2초 / 추론** |
| 메모리 사용 | **34GB** |

### 5-3. 플래너 교체 비교 (같은 주행 기준)

| 플래너 | 시간 |
|---|---|
| Qwen-Drive 플래너 | **1.86초** |
| Alpamayo 1.5 | **4.65초** |

> ⚠️ 두 구간의 도로가 **428m 떨어져 있어** "몇 배 빠르다/느리다"로 일반화할 수 없습니다. 입력 난이도가 다른 비교입니다.

### 5-4. 34B 추론 시간 계산 (이론치 — 영상 저자 계산)

프리필(prefill)과 디코드(decode)를 나눠 계산합니다.

```
프리필 시간 ≈ 2 × 파라미터 수 × 토큰 수   (FLOP 기준)
디코드 시간 ≈ 가중치 전체 크기 ÷ 메모리 대역폭
```

- 글자 하나를 생성할 때도 **64층 전체를 다시 읽습니다** (autoregressive 특성).
- 프리필 FLOP 예시: **373 TFLOP**, KV 캐시: **토큰당 256KB**

| 하드웨어 | 34B 1회 추론 (계산치) |
|---|---|
| NVIDIA DRIVE AGX Thor (차량 탑재, 8비트) | **5.7초** |
| NVIDIA B200 1장 (16비트) | **0.68초** |

- 데이터센터 카드(B200)는 **연산 성능**이, 차량 칩(Thor)은 **대역벽(메모리 대역폭)** 이 병목입니다.
- **Thor는 데이터센터와 정반대로 대역폭이 벽**입니다.

## 6. 버그 리포트 — "판단 문장의 첫 글자가 전부 제비뽑기"

### 증상
- 모델이 출력하는 판단 문장의 **첫 글자가 무작위**로 튄다. (예: 확신에 찬 판단 앞에 엉뚱한 글자)
- 매 실행마다 첫 글자가 달라짐.

### 원인
- **난수 시드(seed) 설정 직후의 첫 번째 샘플링 값이 확률분포를 무시합니다.**
- `torch.manual_seed(...)` 등으로 시드를 고정한 뒤 곧바로 첫 토큰을 뽑으면, 초기화 직후 상태에서 샘플러가 분포 대신 난수 생성기의 첫 출력값을 그대로 취해버리는 현상.
- 두 번째 토큰부터는 정상 분포를 따르므로 **첫 글자만 계속 이상**합니다.

### 해결 방향
1. 시드 설정 후 **더미 추론 1회**를 돌려 첫 난수 값을 소비한 뒤 실제 추론을 시작한다.
2. 또는 sampler에 `temperature=0` (그리디) 또는 `top_p` 정상화가 제대로 적용되는지 확인한다.
3. MLX 이식 시에도 동일 패턴이 재발할 수 있으므로, 시드 고정 + 첫 토큰 검증 테스트를 추가하세요.

```python
# 예시: 더미 토큰으로 첫 난수 소비
import torch
torch.manual_seed(42)
_ = model(dummy_input)          # 첫 난수 값 소비
result = model(real_input)      # 정상 분포로 추론 시작
```

## 7. 왜 0.1초인가 — 속도 기준의 근거

- "얼마나 빨라야 하나"의 **0.1초 기준은 임의 설정이 아니라, Alpamayo 2의 입력 규격에서 나옵니다.**
- 자율주행 파이프라인은 카메라 프레임 주기(약 10Hz ≈ 0.1초)에 맞춰 추론이 끝나야 합니다.
- 현재 MLX 4B(0.64초 탑뷰)는 이 기준에 아직 못 미치고, 34B는 5.7초(Thor 계산치)로 훨씬 깊습니다.

### 그래서 테슬라 FSD는 "글을 쓰지 않는다"

- LLM식 텍스트 토큰 생성은 **디코드 단계에서 가중치 전체를 매 토큰마다 다시 읽어야** 합니다.
- 대역폭 제약이 큰 차량 환경에서 이 방식은 물리적으로 맞지 않습니다.
- **테슬라 FSD가 텍스트 출력을 배제한 것은 취향이 아니라, 대역폭 계산의 결론입니다.**
- 참고: 테슬라 FSD v14 Lite 트립(trip) 가중치는 **0.88GB** — 34B의 1/39 수준입니다.

### 현대차 · NVIDIA의 공통 화법 — 증류(Distillation)

- 같은 시기, 현대차와 NVIDIA 모두 **증류**를 키워드로 내세웠습니다.
- 대형 교사 모델(34B 등)의 지식을 소형 학생 모델(4B 등)으로 옮기는 방식.
- **하지만 증류로 옮겨지지 않는 것이 있습니다:**
  - Qwen-Drive 구조(§1)에서 보듯, ②·③은 ①의 특징 분포에 의존합니다.
  - 교사의 "특징"을 온전히 전달하지 못하면, 탑뷰·판단 품질이 무너집니다.
  - 즉 **부품 교체가 아니라 분포 이전**이 핵심이며, 이것이 증류의 한계이자 과제입니다.
